# Design

## The rule, in one sentence

**The caller decides the answer language; if they do not say, a fixed configured
default answers — never an inference from what retrieval happened to return.**

```
resolve_answer_language(detection, answer_language, conversation_language,
                        languages_in_evidence /* ignored */, default_answer_language)

  1. answer_language, if set and not the "auto" sentinel   -> use it
  2. detection, if present and reliable                    -> detection.language
  3. conversation_language, if set                         -> use it
  4. default_answer_language                               -> the dumb default
```

`languages_in_evidence` is accepted and ignored. It stays in the signature on
purpose: the three ports and the conformance vectors keep an identical argument
list, so the port diff is a *verdict* diff, not an API diff, and a vector can
still assert that a pool full of Telugu changes nothing.

## Why explicit now beats a reliable detection

Old rung 1 was "a reliable detection wins over everything", so
`ask(q, answer_language="fr")` could return German. That is defensible as
"§11: answer in the query language, always" — but it makes the parameter a
suggestion, and the owner's ruling is that the caller's word is the requirement.
A caller who typed a language code has stated an intent that no classifier
outranks; a caller who wants the classifier now says so with `"auto"`.

This is why `"auto"` had to stop being a client-side alias for `None`. Before
this change the two genuinely were the same thing (the client normalised `"auto"`
to `None` and nothing ever detected). Now they are three distinct behaviours:

| call | behaviour |
|---|---|
| `ask(q)` | configured default. Predictable, corpus-independent. |
| `ask(q, answer_language="auto")` | detect from the **question** |
| `ask(q, answer_language="ta")` | Tamil, unconditionally |

## Why the evidence rung is removed rather than kept under `auto`

The task left this open. **Removed outright.** Under `"auto"` the caller has
asked for *"detect from my question"* — falling from an unreliable question
detection into the evidence pool answers a question nobody asked, and it is the
exact inference that stamped 15 of 22 English answers `te`/`ta`. It would also
mean `"auto"` silently changes behaviour as the corpus changes, which is the
unpredictability the ruling rejects. An unreliable detection under `"auto"`
therefore falls to the default like everything else.

Keeping it "reachable only under auto" would additionally leave the port authors
maintaining a rung with no reachable, defensible test case.

Evidence languages are not lost — `EvidenceSignals.languages_in_evidence` still
reports them. They stop being an *input* and stay an *observation*.

## Ingest reuses this function — do not break it

`ingest/pipeline.py::_detect_language` (not owned by this change) calls
`resolve_answer_language(detection=…, default_answer_language=…)` to stamp a
DOCUMENT's language. Rung 2 is what that call relies on, which is another reason
rung 2 stays where it is: with `answer_language` and `conversation_language`
absent, the chain is exactly "reliable detection, else default", which is the
correct document-language rule and is unchanged by this proposal.

## Conformance impact (`conformance/cases/language.json`)

**Regenerated by the conformance owner, not here.** Existing 6 vectors:

| # | vector name | old expected | new expected | why |
|---|---|---|---|---|
| 1 | rung 1: reliable detection wins over everything | `ta` | **`fr`** | explicit `answer_language="fr"` now outranks the reliable `ta` detection |
| 2 | rung 2: unreliable detection -> explicit override | `fr` | `fr` | unchanged |
| 3 | rung 3: no detection, no override -> conversation language | `de` | `de` | unchanged |
| 4 | rung 4: dominant evidence language | `es` | **`en`** | evidence rung removed; falls to `default_answer_language: "en"` |
| 5 | rung 4 tie: first-seen evidence language wins (stable) | `fr` | **`en`** | evidence rung removed; falls to `default_answer_language: "en"` |
| 6 | rung 5: nothing else -> configured default | `hi` | `hi` | unchanged |

Vectors 1, 4 and 5 should also be **renamed** — they no longer describe the rung
they are named after. Suggested: *"explicit override beats a reliable
detection"*, *"evidence language is ignored"*, *"evidence tie is ignored"*.

Three vectors should be **added** so the new rule is pinned rather than inferred:

| name | inputs | expected |
|---|---|---|
| explicit override beats everything | `detection={ta,0.95,reliable}`, `answer_language="ta"`… any conversation/evidence | `ta` |
| reliable detection is used when nothing is explicit | `detection={ja,0.99,reliable}`, no override, no conversation, `languages_in_evidence:["ta","ta"]`, default `en` | `ja` |
| a pool full of foreign evidence changes nothing | `detection=null`, no override, no conversation, `languages_in_evidence:["te","te","te"]`, default `en` | `en` |

The `"auto"` sentinel is deliberately **not** a conformance vector: it is
resolved above this function (in the flow, where the detector lives), so pinning
it here would pin the wrong layer.

## Task 2 — refusal attribution

The bug is one line doing two jobs:

```python
reason = _capability_reason(unsupported) or "no sufficiently relevant evidence found"
```

`unsupported` is the union of the script gaps of the **question and every pooled
candidate**, so one unreadable passage anywhere in the top-k rewrote the reason
for an unrelated, purely-English refusal. Measured: 11 of 14.

The pool is now PARTITIONED rather than unioned — `readable` decides what may be
cited, `blocked` is the only thing a script-attributed reason may be blamed on —
and `missing_evidence[0]` is the ONE cause that produced the refusal, with the
capability note appended after it, never in place of it.

1. **the question is unreadable** → `unsupported script: …`. Unchanged; this is
   the one case where the gap is the whole story.
2. **nothing readable was relevant**:
   - **every** candidate was excluded for its script →
     `no readable evidence found; unsupported script: <scripts>`. The gap is the
     only thing between us and the pool, so it is the cause.
   - some of the pool was readable and none of it was relevant →
     `no sufficiently relevant evidence found`, **plus** the unreachable note as
     a second entry when anything was blocked. Saying the script was the cause
     here sends the caller after a phantom: we read part of the corpus and it was
     silent. Saying nothing about the gap would hide it. Both, in order.
3. **the gate rejected every generation** → `generated answer failed the
   faithfulness gate` first, with the unreachable note appended if any. What was
   in the rest of the pool did not cause the gate to fire.

The primary/additive split is the whole fix: the old code chose *between* the two
reasons, and the capability one always won.

`EvidenceSignals.unsupported_scripts` keeps reporting the full observed gap in
every case — it is an observation, and narrowing it would lose the very signal
Task 3 needs. Only the *reason string* is narrowed.

## Task 3 — unreachable authority: signal, do not refuse

**Decision: surface it, keep the answer.** The answered Result carries

- `evidence.unsupported_scripts` — the scripts of pooled candidate documents that
  were excluded because the tokenizer does not claim them (already an additive,
  empty-by-default CAPABILITY signal, so no schema change and no serialization
  change for any corpus without an unclaimed script), and
- one line in `missing_evidence` naming the excluded **documents** and scripts —
  appended after the real reason on a refusal, and the only entry on an answered
  Result,
  so the gap is legible in the text channel a human reads, not only in a tuple a
  program reads.

`missing_evidence` on an answered Result is additive (`()` today) and reads
correctly: material that bears on the question and is missing from the answer.

### Why not downgrade to a refusal

Refusing whenever the partition holds an unreadable candidate deletes a correct,
cited, authoritative answer because a corpus contains one byte the tokenizer will
not claim — a single Telugu footer or a Khmer appendix takes an entire English
corpus dark. That trades a *rare* wrong answer for a *systematic* non-answer, and
it does it invisibly at ingest time, where nobody is looking. Cite-or-abstain
requires that what we DO say is grounded; it does not require abstaining because
something we cannot read exists nearby.

### Two rejected alternatives, and why

1. **Refuse when an unreadable candidate outranks the cited one.** Superficially
   principled — retrieval itself judged it better evidence. It does not fire on
   the measured case: the query was English and the annexure Telugu, so BM25 `tf`
   is zero across the board and the annexure can never outrank. A rule that
   misses the case that motivated it is theatre.
2. **Infer supersession from the unreadable passage** ("states it overrides"). We
   cannot read it. Asserting anything about its content is exactly the ungrounded
   claim the library exists to refuse.

The real fix for the measured case is claiming the script (a concurrent change
adds Telugu) or ingest-time authority metadata (ADR-0004 — an annexure that
overrides is a higher tier, and that is metadata, not text). This change makes
the residue **loud** instead of silent, which is what a caller needs to escalate.
A caller that must be hard-safe can do so in one line:

```python
if result.evidence.unsupported_scripts:
    escalate(result)          # "I answered, but there is material here I cannot read"
```

## Not in scope

- Localised refusal strings (still the English shell).
- Translating citations. `SourceRef.passage` stays verbatim in its source
  language; `translation` remains additive and unused here (§11, §16).
- `search_languages` behaviour. Search language and answer language stay
  independent by construction.
